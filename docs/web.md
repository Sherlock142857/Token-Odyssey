# localhost 单 act 测试台

> **职责：** 为一个 Act 提供 Human/LLM/Scripted 热座测试与作者调试视图。输入是 Scenario v3、可选 RunConfig v3 和浏览器动作；输出仍通过 ActRunner、WorldHarness 与 Run Log v4 产生。HTTP DTO 只投影运行数据，不构成新的世界权威。

## 启动

在项目根目录、已安装项目的环境中运行：

```bash
token-odyssey web --run-config configs/llm.local.yaml
```

打开 http://localhost:8000。在设置页选择 Andy 为 Human、Morgan 和 Clara 为 LLM。
网页可以选择每位角色的控制方式和模型 profile、最大轮数、随机种子。
直到点击“开始 Act”才会调用模型；密钥由所选 backend 从服务端配置读取。

使用 LLM profile 会产生 API 费用，输出具有非确定性。运行目录会保存 prompt、回复、角色私有想法、
Observation 与 token 用量；不会写入 API key，但仍应把 `runs/` 当作敏感数据。

```bash
# 离线体验：探索者人类，其他角色脚本。
token-odyssey web

# 自定义场景、端口、日志目录和单次模型调用超时（秒）。
token-odyssey web --scenario scenarios/floodgate_dispatch.yaml \
  --run-config configs/llm.local.yaml --port 8080 --runs-dir runs --llm-timeout 90
```

界面使用原生 HTML/CSS/JavaScript 和 Python 标准库 HTTP 服务，无需 Node、npm 或前端构建。
静态文件随 Python 包一起安装，不引用 CDN 或远程字体。

## 交互安排

- 顶部持续显示 act 名称、已完成轮数、行动权和事件计数、当前执行角色、等待或结束状态。
- 左栏保留当前人类角色的内心想法与当前牵挂、房间、随身物品、可见物品、在场角色和出口。
  明确标注这些是最近一次决策时的状态；其他角色行动期间不会额外扫描刷新。
  首次辨认的描述会保留。历史已知对象单独折叠，不暗示当前位置仍然有效。
- 中栏日志独立滚动。“角色日志”只使用该角色获准的观测；“World Log”是明确标记的作者测试视角，
  显示世界事件、失败反馈、机关因果及可展开的结构化变化。
  默认跟随最新记录；向上滚轮或取消勾选可阅读旧记录，“回到最新”恢复跟随。
- 右栏只在当前人类角色获得行动权时启用。选择动作、选择目标、加入队列、调整顺序、提交。
  `say` 使用文本框；其他动作全部用下拉、点选或勾选；可选显著程度默认为普通。
  点左栏物品可以填入兼容的当前表单，或打开适合该物品的动作。
- 自动推进遇到任何人类回合会暂停。取消自动推进后，每次提交只完成一个行动权；再用顶部按钮继续。
  LLM 计算在后台串行进行，页面保持响应。“回合后暂停”和“结束测试”会等待正在处理的回合完成。
- 多个人类角色共用本地页面，轮到谁默认显示谁；也可以切换查看人类角色。
  这是单机轮流操作的测试台，没有多用户登录或角色身份认证。

所有动作都经 `HumanAgent.submit → ActRunner.step → WorldHarness` 执行。
表单选项来自获准的角色 DTO 和历史观测，不查询世界真值来预判可执行性。
因此能看到的对象仍可能无法接触，钥匙也可能不匹配；实际失败由原有动作规则反馈。
出口 DTO 没有开闭/锁能力列表，因此出口可作为开关、解锁候选；不支持的操作由原有规则拒绝。

## 队列、失败与结束

队列长度遵守场景 `max_actions`。默认成功移动后结束队列；后续动作失败保留已成功前缀。
刚刚打开或搜索发现的对象不能追加进已经提交的决定，需要等下次获得行动权。

首个动作失败时，界面显示中文原因和新的修正请求；修正次数由原有 `max_retries` 决定。
修正耗尽后，运行器自动等待。HTTP 层拒绝格式错误、过期请求、重复提交和错误角色，
这些请求不会额外推进世界。提交成功的决定不会因为刷新而重做。

`completed` 表示达到 `end_when`；`limit_reached` 表示轮数耗尽，不能视为剧情成功。
结束时保存原有运行产物，并执行 `expected` 检查和 `replay_run`，生成 `mode: web` 的 `acceptance.json`。
World Log 测试区展示各条件、回放是否一致和模型 token 用量。
只有 act 完成、全部声明条件满足、回放一致才显示“全流程验收通过”。

模型连接异常显示中断状态，记录已提交动作并保留失败 manifest，不将传输故障伪装成角色等待。
网页入口默认每次模型请求超时 60 秒，不启用 SDK 传输重试；模型格式修正仍使用原有运行器策略。
这项设置仅在网页组合层生效，不改变 CLI 或供应商实现。可用 `--llm-timeout` 调整。

## 恢复与数据边界

刷新网页通过只读 `/api/state` 重新获得同一个内存运行实例；当前待提交队列在同一浏览器标签的
`sessionStorage` 中按运行 ID 和请求 ID 保留。服务重启后不能恢复未结束运行，需开始新测试。
已结束的目录仍能用 `token-odyssey replay runs/<run-id>` 检查。

每个服务进程只有一个共享 act，支持一个串行工作线程，避免多个浏览器同时推动运行器。
状态、角色视图、历史描述和日志都由已发布记录缓存生成。GET 不调用 `step`、`scan` 或 `view`，
不会改变随机数、消耗角色 inbox 或清空反馈。

`/api/catalog` 仅公开场景公共背景、角色名称、可用 profile 名称/模型和动作 schema。
`/api/state` 只提供人类角色的授权视图、私人身份资料和自身动作反馈，不包含其他角色目标、机关规则、
世界状态或原始模型对话。`/api/observer` 单独提供作者事件及验收数据，只在用户切到 World Log 时请求。
两者的分离用于避免把作者数据误混入玩家操作界面，不作为多用户权限隔离。

服务器仅绑定 `127.0.0.1`；检查 Host / Origin，写入接口还校验页面会话令牌。
静态资源使用固定白名单，不公开项目文件、API key 或运行目录。

## 验证

```bash
pytest
```

`tests/test_web.py` 覆盖人类＋脚本、人类＋真实 LLM 会话/翻译器（离线模拟 API）两条完整流程，
包括封存圣杯场景故意安排的后续失败；最终世界、事务、观测和角色视图与原有脚本验收逐字节一致。
另覆盖 HTTP 边界、刷新不重采样、重复/过期提交、失败后修正、多角色轮流操作、轮数终止、
后台模型阻塞时只读状态仍响应，以及模型传输失败。
HTTP 集成测试需要允许绑定 localhost 临时端口，不调用真实模型。

## 角色简报与交互 Router

当前默认场景为“Greyhaven：暴雨后的药箱”，人类扮演 Andy，Morgan 和 Clara 可逐个选择控制器。开始后即显示选定人类角色的身份外貌、性格、内心想法与当前牵挂、本幕背景与记忆，不需要等首次获得行动权。当前房间/背包仍以真正生成的决策视图为准；刷新不会触发新的扫描。

玩家事件日志和 LLM 输入共用事实转述入口。动作在视听授权后合成事实：具名台词只显示一次，具体物品操作覆盖模糊摆弄，移动直接显示获准的出发/目的房间。机关的视觉与声音互补描述合成同一段文字。

热座切换只返回所选人类角色的待处理请求，不将另一名人类的pending视图混入当前DTO。角色简报会随选择切换；所有角色的路由依据只在World Log测试视角显示。

加权模式的轮数是行动预算单位。观察者页面可展开Router查看最近一次选择的概率、等待年龄、关注值及其感知证据；完整历史在routing.jsonl中。动作失败信息直接使用服务端提供的中文messages，显示队列失败和no-op提示。
